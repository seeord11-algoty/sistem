Docker y Kubernetes: arquitectura, funcionamiento y aplicaciones

Grupo 3 · Sebastian Ordoñez · Yeison Lamadrid · Miguel Yela

Buenos días. Somos el grupo 3 y nuestro tema es contenedores: Docker y Kubernetes. La imagen no es casualidad: así como el contenedor de carga estandarizó el transporte marítimo, los contenedores de software estandarizaron cómo empaquetamos y desplegamos aplicaciones. Usen las flechas para avanzar; varias diapositivas son interactivas.

Ruta de la exposición

Nueve contenedores, una sola carga

Cada parte que pidió el profesor es un contenedor. Toquen cualquiera para saltar a esa sección.

Objetivo: explicar cómo el sistema operativo aísla y limita procesos para ejecutar aplicaciones con virtualización ligera, y cómo Kubernetes las administra a escala.

Esta es la ruta: los nueve puntos que pide la guía. Primero contexto, luego la teoría del sistema operativo que hace posibles los contenedores, después cómo funcionan Docker y Kubernetes por dentro, herramientas, casos reales, ventajas y desventajas, una demostración y cierre.

1 · Introducción

El software dejó de viajar suelto

En 1956 el contenedor estándar cambió el transporte de carga: no importa qué lleve adentro, todos los barcos y grúas lo manejan igual. Docker hizo lo mismo con el software: empaqueta la app con sus librerías y configuración para que corra igual en el portátil, el servidor o la nube.

Antes, instalar una aplicación era pelear con versiones: "en mi máquina sí funciona". El contenedor resuelve eso empacando la aplicación con todo lo que necesita. Y no es una moda: según la encuesta de la CNCF publicada en enero de 2026, el 98% de las organizaciones usa tecnologías cloud native y el 82% de quienes usan contenedores ya corre Kubernetes en producción. Para nosotros como ingenieros de sistemas es la forma estándar de desplegar software.

IBM (Felter et al., 2015): con Docker el rendimiento fue igual o mejor que con KVM en casi todos los casos; ambos requieren ajustes para cargas intensivas en I/O.

La diferencia clave: una máquina virtual emula hardware y cada una carga su propio sistema operativo completo. Un contenedor no trae sistema operativo: comparte el kernel del anfitrión y solo empaqueta la aplicación y sus librerías. Si resaltamos, se ve que las VM repiten tres sistemas operativos; los contenedores usan uno. Por eso arrancan como un proceso y pesan megabytes. El estudio de IBM de 2015 midió que los contenedores rinden igual o mejor que KVM en casi todo. A cambio, como comparten kernel, el aislamiento es más débil.

2 · Fundamentación teórica

Dos piezas del kernel hacen el truco

Namespaces: lo que el proceso puede ver

Dentro del contenedor

En el host

cgroups: lo que el proceso puede gastar

8 MiB usados

Corriendo · docker run --memory=128m

Kubernetes 1.37 recomienda migrar a cgroup v2: el soporte de cgroup v1 se retirará.

Aquí está el corazón del tema de sistemas operativos. Un contenedor es un proceso normal de Linux con dos cosas: namespaces y cgroups. Los namespaces controlan lo que el proceso puede ver: por ejemplo, dentro del contenedor nginx cree que es el proceso 1, pero en el host tiene otro PID. Los cgroups controlan lo que puede gastar: si le ponemos 128 MiB de memoria y se pasa, el kernel lo mata, que es el famoso OOMKilled con código 137. Pruébenlo con el botón.

Las instrucciones que cambian archivos (RUN, COPY, ADD) crean capas; se apilan con un sistema de archivos de unión (OverlayFS).

0 contenedores

Toquen «docker run» para crear contenedores desde la misma imagen.

Todos comparten las tres capas; cada uno solo agrega una capa de escritura delgada (copy-on-write).

Estándar OCI (Linux Foundation, junio de 2015): tres especificaciones ImagenRuntimeDistribución Por eso una imagen hecha con Docker corre en containerd, CRI-O o Podman.
La imagen es la plantilla: es de solo lectura y está hecha por capas: cada instrucción que cambia archivos en el Dockerfile, como COPY o RUN, agrega una. El contenedor es una instancia en ejecución de esa imagen. Si hacemos docker run tres veces, no se copian las capas: los tres contenedores comparten la misma imagen y cada uno solo agrega una capa de escritura. Y todo esto está estandarizado por la OCI desde 2015, por eso las imágenes son portables entre herramientas.

2 · Fundamentación teórica

47 años de aislar procesos

Los contenedores no nacieron con Docker. En 1979 Unix ya tenía chroot para cambiar la raíz del sistema de archivos de un proceso. Luego vinieron las jails de FreeBSD y LXC en Linux. Docker en 2013 lo hizo fácil, Kubernetes en 2014 resolvió la administración a escala y en 2015 se creó el estándar OCI. En 2022 Kubernetes dejó de usar Docker directamente y en agosto de 2026 salió la versión 1.37.

Docker es cliente-servidor. El comando que escribimos lo recibe la CLI y lo manda como petición a la API REST del daemon, dockerd. Si la imagen no está, se descarga del registry, normalmente Docker Hub. Luego dockerd le pasa el trabajo a containerd, que maneja el ciclo de vida; el shim queda como padre del contenedor, y runc es el que de verdad habla con el kernel para crear los namespaces y los cgroups. Vamos paso a paso con el botón.

3 · Arquitectura y funcionamiento

Kubernetes: el timonel de miles de contenedores

Plano de control
Pendientes (sin nodo):ninguno

Listas 0 de 3

Toquen un componente para ver qué hace.
    Kubernetes significa timonel en griego. Tiene un plano de control: el API server es la puerta de entrada, etcd guarda todo el estado, el scheduler decide en qué nodo va cada pod y el controller manager corrige diferencias. En cada nodo, el kubelet garantiza que los contenedores corran. Hagamos la prueba: si elimino un pod, el controlador ve que hay 2 de 3 y crea otro solo; eso es autorreparación. Si subo las réplicas, el scheduler las reparte. Y si apago un nodo, sus pods se vuelven a crear en los otros; si no hay espacio, quedan pendientes.

    3 · Arquitectura y funcionamiento

    Uno declara el estado; Kubernetes lo cumple

    
    
    
      
      
    Pasen el cursor por el YAML para ver qué significa cada parte.
    
      
    
        Docker y Kubernetes hoy
        
    Desde la versión 1.24 Kubernetes ya no trae dockershim: el kubelet habla por CRI con containerd o CRI-O, que usan runc. Las imágenes hechas con Docker siguen funcionando porque son OCI.
    
      
    
    
    
  
    
  
    En Kubernetes no damos órdenes paso a paso: escribimos un archivo YAML con el estado que queremos, por ejemplo tres réplicas de nginx con límite de 128 megas. Los controladores observan el estado real, lo comparan con el deseado y actúan hasta igualarlo, en un bucle infinito. Fíjense que el límite de memoria del YAML termina siendo un cgroup del kernel. Y una pregunta típica: Kubernetes ya no usa Docker directamente desde la 1.24, pero las imágenes de Docker sí sirven porque siguen el estándar OCI.
    

    



    
  
    4 · Herramientas tecnológicas
    
  
    La caja de herramientas del puerto
    
  
    
  
    
  
    Estas son las herramientas principales, por categoría. Para construir y ejecutar: Docker Engine, Desktop, Compose y Podman. Los runtimes son containerd, CRI-O y runc. Las imágenes se guardan en registros como Docker Hub o Harbor. Para orquestar está Kubernetes, que se puede correr local con minikube, kind o k3s, o gestionado en la nube con GKE, EKS o AKS. Y alrededor hay un ecosistema: Helm para paquetes, Prometheus y Grafana para monitoreo, Argo CD para GitOps y Trivy para revisar vulnerabilidades.

    6 · Ventajas y desventajas
    
  
    Ligeros y portables, pero no blindados
    
  
    
    
    Ventajas
    
    
    Desventajas y dificultades
    
    
    
      
      
    «Leaky Vessels» (CVE-2024-21626). En runc 1.1.11 y anteriores, una fuga de descriptor de archivo permitía que un proceso del contenedor quedara trabajando dentro del sistema de archivos del host: escape del contenedor. Se corrigió en runc 1.1.12.
    
      
    47% señala el cambio cultural en los equipos como la barrera número uno (CNCF, 2026).
    
    
    
  
    
  
    Las ventajas son claras: ligeros, portables, más aplicaciones por servidor y, con Kubernetes, escalado y autorreparación. Pero no están blindados: como comparten kernel, una falla puede permitir escapar al host, como pasó con Leaky Vessels en 2024, una vulnerabilidad en runc. Kubernetes además es complejo de aprender y operar, los datos persistentes requieren cuidado, y según la CNCF la barrera número uno hoy no es técnica sino cultural.

    8 · Conclusiones
    
  
    Lo que nos llevamos
    
  
    
    
    No es magia, es el kernel.
    Un contenedor es un proceso con namespaces y cgroups. Ese es el puente directo con Sistemas Operativos.
    
    
    Docker empaqueta, Kubernetes opera.
    Docker resolvió construir y distribuir; Kubernetes, administrar a escala. Se complementan.
    
    
    Ligereza a cambio de aislamiento.
    Frente a las VM ganan en velocidad y densidad, pero comparten kernel; en producción se combinan.
    
    
    Una habilidad base del oficio.
    Despliegue, DevOps, nube e IA pasan por aquí: un ingeniero de sistemas tiene que dominarlo.
    
  
    
  
  
    Para cerrar, cuatro ideas. Primero, los contenedores no son magia: son funciones del kernel bien empaquetadas. Segundo, Docker y Kubernetes no compiten: uno empaqueta y el otro opera. Tercero, ganamos ligereza pero perdemos algo de aislamiento, por eso en producción se combinan con máquinas virtuales. Y cuarto, es una habilidad básica para cualquier ingeniero de sistemas hoy.
